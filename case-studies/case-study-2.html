Portfolio / Case Study #2

Dashboard Design & Optimization

Transforming a 45-second dashboard load time into a 5-second powerhouse through system redesign and stakeholder collaboration.

Full Feeling Inc. (Dohtonbori Philippines)
Digital Marketing & PR Officer
Mar 2024 – Jun 2024

Executive Summary

This case study demonstrates how business analysis principles—requirements gathering, system optimization, and iterative refinement—can dramatically improve reporting infrastructure and stakeholder adoption. By conducting systematic stakeholder interviews, redesigning Excel architecture, and optimizing data workflows, I reduced dashboard load time by 90% while increasing user adoption from 42% to 87%.

Key Results

  • 90% performance improvement: 45 seconds → 5 seconds load time
  • 86% file size reduction: 85MB → 12MB
  • 10+ stakeholders managed across 6 branches
  • 105% adoption increase: 42% → 87% monthly active users
  • Data quality standards established across branches

Context

Full Feeling Inc. is a multi-branch hospitality and food retail business operating across 6 locations in the Philippines. The company had invested in building a comprehensive Excel-based dashboard to track sales, inventory, customer engagement, and financial metrics across all branches.

However, the dashboard had become unwieldy: 85MB file size, 50+ sheets, and a crippling 45-second load time. Users were frustrated. Adoption was low (42% monthly active users). Branch managers often reverted to manual reporting because waiting for the dashboard to load was slower than pulling the data manually.

The business wanted a fast, reliable reporting system that all 10+ stakeholders (branch managers, finance, marketing, operations) would actually use.

The Problem

Dashboard Performance Crisis

  • 45-second load time: Unacceptable user experience. Users abandoned the dashboard.
  • 85MB file size: Too large; slow network transmission; prone to corruption.
  • 50+ interconnected sheets: Complex dependencies; changes in one sheet cascaded across many; difficult to troubleshoot.
  • Manual data entry points: Multiple users manually entering data into different sheets; high error rates.

Low Adoption (42%)

Users didn't regularly use the dashboard because it was slow. They'd wait 45 seconds to get data that was often outdated or incorrect anyway. Manual reporting seemed faster.

Data Quality Issues

Different branches entered data differently. No standardized data entry process. Quality checks were sporadic. The more data flowing in, the more errors propagated.

Requirements Gathering

Stakeholder Interviews

I conducted interviews with 10+ stakeholders across 6 branches to understand:

  • What data each person actually needs (vs. what they thought they needed)
  • How frequently they access the dashboard
  • What pain points prevented adoption
  • What data quality issues they'd observed

Key Findings

  • Role-based needs: Branch managers needed sales + inventory data. Finance needed payment reconciliation. Marketing needed campaign performance. Different roles needed different views.
  • Frequency varied: Finance checked daily; branch managers weekly; marketing monthly. The current design tried to serve all users equally, but that was inefficient.
  • Pain point #1 - Speed: 45-second load time was unacceptable. Users wanted sub-5-second response times.
  • Pain point #2 - Accuracy: Users didn't trust the data. They'd verify it manually before making decisions.
  • Pain point #3 - Complexity: Too many sheets. Users didn't know which sheet to look at for specific questions.

Requirements Synthesis

Based on stakeholder feedback, the redesigned dashboard needed to:

  • Load in under 5 seconds (10x performance improvement)
  • Separate views by role (Branch Manager Dashboard, Finance Dashboard, Marketing Dashboard)
  • Establish data quality standards and automated validation checks
  • Automate data pulls from source systems (remove manual entry where possible)
  • Provide clear documentation so users understood which data came from which source

Solution Design & Implementation

Architecture Redesign

Before: Single massive 85MB file with 50+ interconnected sheets pulling data manually.

After: Multi-tiered architecture:

  • Data Layer: 3 source files pulling live data from branch systems (sales, inventory, finance) — automated overnight refresh
  • Processing Layer: Consolidated data sheet performing calculations and validation checks
  • Presentation Layer: 3 separate role-based dashboards (Branch Manager, Finance, Marketing) — each under 10MB

Performance Optimization

  • Removed unnecessary data: Eliminated historical data older than 2 years (users rarely accessed it)
  • Optimized formulas: Replaced inefficient VLOOKUP chains with INDEX/MATCH; moved heavy calculations to data layer
  • Automated overnight refresh: Data updates happen at 2 AM when system load is low; users open fast, pre-calculated file at 8 AM
  • Reduced pivot tables: Pre-calculated summaries instead of live pivot tables (faster rendering)

Data Quality Standards

  • Defined standard data entry formats across branches
  • Built validation checks: alerts when data falls outside expected ranges
  • Created data dictionary explaining every metric's source and calculation method
  • Designated data steward per branch responsible for quality

User Experience

  • Created simplified dashboards: 5-7 key metrics per role (not 50+ sheets)
  • Added filter controls: branch, date range, product category
  • Included data confidence indicators: "Last updated at 8:15 AM today"
  • Provided help documentation and quick-reference guides

Results & Business Impact

Quantified Outcomes

  • Performance: 45 seconds → 5 seconds (90% improvement)
  • File Size: 85MB → 12MB (86% reduction)
  • User Adoption: 42% → 87% monthly active users (2x increase)
  • Data Quality: Validation rules caught ~15-20 data errors per month that would have propagated
  • Stakeholder Satisfaction: 10/10 stakeholders reported the redesigned dashboard as "significantly improved"

Strategic Impact

Adoption: From 42% to 87% monthly active users — a 105% increase. Users now proactively consult the dashboard instead of viewing it as a burden.

Decision Velocity: Branch managers can now make faster decisions. Instead of waiting 45 seconds (or pulling data manually), they open the dashboard in 5 seconds and have the information they need.

Data Trust: The data quality standards and validation checks increased user confidence. Users now trust the dashboard enough to make decisions based on it without manual verification.

Reduced Reporting Burden: Finance team previously spent 2-3 hours weekly reconciling manual reports. Automated data pulls reduced that to 30 minutes, freeing time for analysis.

Key Learnings

1. Stakeholder Interviews Are Non-Negotiable

I could have guessed that "performance" was the main issue. But interviews revealed a more nuanced problem: users didn't trust the data quality, so even a fast dashboard wouldn't help if data was unreliable. Interview investment paid off.

2. Separate Presentations for Different Users

A single dashboard tried to serve everyone. That's impossible. By creating role-based dashboards, each user saw only what mattered to them. Adoption skyrocketed because users found their dashboard useful, not bloated.

3. Performance Matters More Than Feature Count

The redesigned dashboard had fewer features than the original (removed some nice-to-have reports). But it was 10x faster. Users chose speed over feature completeness. Speed = adoption.

4. Data Quality Standards Are Foundation

A fast dashboard with bad data is useless. The automation + validation checks were as important as the performance optimization. Trust in the system is what drives adoption.

Conclusion

This case study demonstrates how systematic business analysis—deep stakeholder understanding, clear requirement definition, thoughtful system design, and iterative refinement—transforms technology from a burden into an asset.

The redesigned dashboard wasn't magic. It was the result of understanding what users actually needed, designing a system to meet those needs, and optimizing relentlessly for speed and trust.

Business Analyst Takeaway: When a system has low adoption, the answer usually isn't "more features." It's usually "understand the user's real pain point and eliminate it." In this case, that pain point was speed and data reliability. Once solved, adoption followed naturally.
